# README — Перенос баз данных SQL Server

Простой графический скрипт на PowerShell для переноса баз данных SQL Server в другое место на диске. Вместо того чтобы вручную писать `ALTER DATABASE ... MODIFY FILE`, копировать файлы через проводник и молиться, что ничего не отвалится — открываете окошко, ставите галочки, жмёте кнопку.

---

## Что он умеет

- Показывает список всех ваших баз данных (системные — `master`, `model`, `msdb`, `tempdb` — автоматически скрыты, их этим скриптом трогать нельзя).
- Для каждой базы видно:
  - сколько у неё файлов,
  - **где файлы лежат сейчас**,
  - состояние (Normal, Offline и т.д.),
  - назначение (если вы заполняли расширенное свойство `Description` у базы).
- При наведении курсора на имя базы или на путь — всплывает подсказка со списком всех файлов: логическое имя, тип (`ROWS`/`LOG`), размер и полный путь.
- Генерирует SQL-скрипты для переноса, чтобы вы могли их **прочитать глазами** до выполнения.
- Умеет **физически перемещать файлы** — одной галочкой.

---

## Что нужно, чтобы запустить

1. **Windows** и **PowerShell 5.1** (встроенный, ничего ставить не надо).
2. Модуль **SqlServer** (или хотя бы сборки SMO). Проверить:

   ```powershell
   Get-Module -ListAvailable SqlServer
   ```

   Если пусто — поставьте:

   ```powershell
   Install-Module -Name SqlServer -Scope CurrentUser
   ```

3. Права:
   - ваша учётная запись должна уметь **читать** метаданные SQL Server и **перемещать файлы** по диску;
   - учётная запись **службы SQL Server** должна иметь **полный доступ** к новой папке (иначе база после переноса не откроется). Это самый частый источник проблем — см. раздел «Если что-то пошло не так».

---

## Как запустить

1. Сохраните скрипт, например, в `C:\Scripts\Move-DatabasesGUI.ps1`.
2. Откройте PowerShell и выполните:

   ```powershell
   Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
   C:\Scripts\Move-DatabasesGUI.ps1
   ```

   Первая команда разрешает запуск скриптов только в текущем окне PowerShell — это безопаснее, чем менять политику на всю систему.

3. Появится окно. Дальше — по шагам.

---

## Как пользоваться (по шагам)

### Шаг 1. Подключиться

Вверху укажите сервер (по умолчанию `localhost`), выберите способ входа — Windows-аутентификация или логин/пароль SQL — и нажмите **«Подключиться»**. Появится таблица с базами.

### Шаг 2. Выбрать базы и новый путь

- Отметьте галочками базы, которые хотите перенести.
- В поле «Новое расположение файлов» укажите папку, куда их положить (например, `D:\SQLData`). Кнопка **«Обзор...»** открывает обычный выбор папки.
- Если хотите **реально переместить файлы**, поставьте галочку **«Физически перемещать файлы (Move-Item)»**. Если не поставить — скрипт только поменяет записи о путях в метаданных (полезно для отладки, но база после этого не заработает, если файлы не перенести руками).

### Шаг 3. Сгенерировать скрипты и проверить

Нажмите **«Сгенерировать скрипты»**. В нижнем поле появятся SQL-запросы, которые скрипт собирается выполнить. Прочитайте их. Если всё ок — жмите **«Выполнить»**.

### Шаг 4. Выполнить

Появится подтверждение — там будет написано, что именно произойдёт:
- с галочкой: OFFLINE → перемещение файлов → MODIFY FILE → ONLINE;
- без галочки: только MODIFY FILE.

После нажатия «Да» в нижнем поле будет **лог** — что сделано по каждой базе, какие файлы куда переехали, где были ошибки.

## Что происходит «под капотом» при физическом переносе

Для каждой выбранной базы скрипт делает строго по порядку:

1. **`ALTER DATABASE [db] SET OFFLINE WITH ROLLBACK IMMEDIATE`** — SQL Server закрывает файлы, они становятся свободны для перемещения. Все активные соединения с базой при этом обрываются.
2. **`Move-Item`** — реально переносит `.mdf`/`.ndf`/`.ldf` в новую папку. Скрипт проверяет, что исходный файл существует, а целевого ещё нет — чтобы случайно не перезаписать чужой файл.
3. **`ALTER DATABASE ... MODIFY FILE (...)`** — говорит SQL Server: «файлы теперь по новым путям».
4. **`ALTER DATABASE [db] SET ONLINE`** — база открывается уже с новых путей.

Шаг 4 выполняется **в любом случае** — даже если на шаге 2 или 3 что-то упало. База не останется висеть в `OFFLINE`.

## ⚠️ Прочитайте перед первым запуском

- **Сделайте резервную копию.** Это не формальность — это правило. Перенос файлов необратим, если что-то пойдёт не так.
- **Не используйте этот скрипт для системных баз** (`master`, `model`, `msdb`, `tempdb`). Их перенос делается вручную с остановкой службы SQL Server. Скрипт их и не показывает, но на всякий случай предупреждаю.
- **Права на папку для службы SQL Server.** Ваш пользователь может спокойно двигать файлы, но если сервис SQL Server не имеет доступа к целевой папке — база после переноса уйдёт в `Recovery Pending`. Дайте `Full Control` учётке сервиса заранее:

  ```powershell
  # Узнать, под кем работает SQL Server:
  Get-Service MSSQLSERVER | Select-Object -ExpandProperty StartName
  ```

- **Никто не должен работать с базой** в момент переноса. Скрипт оборвёт соединения, но пользователи получат ошибку — лучше предупредить их заранее.
- **Проверьте свободное место** на новом диске. `Move-Item` не сжимает — нужно столько же, сколько занимают файлы (плюс небольшой запас).
- **Не переносите базы, которые сейчас в `Restoring` или `Offline`** — сначала приведите их в нормальное состояние.

## Если что-то пошло не так

**«Ошибка подключения»**
- Проверьте имя сервера, логин/пароль, включён ли протокол TCP/IP в конфигурации SQL Server.
- Для именованного экземпляра имя сервера указывается как `SERVER\INSTANCE`.

**База после переноса ушла в `Recovery Pending` / `Suspect`**
- Почти наверняка у службы SQL Server нет прав на новую папку. Проверьте и дайте права, потом `ALTER DATABASE [db] SET ONLINE`.

**«Целевой файл уже существует»**
- В новой папке уже лежит файл с таким же именем. Скрипт специально не перезаписывает — уберите старый файл вручную или укажите другую папку.

**«Файл не найден: ...»**
- Исходного файла нет на месте. Такое бывает, если база уже была перенесена раньше или файлы руками сдвинули. Проверьте колонку «Текущее расположение» перед запуском.

**Ошибка при `SET ONLINE`**
- В логе будет видно, на какой базе. Чаще всего — права или файл повреждён/недоступен. База останется в `OFFLINE`, файлы уже на новом месте — можно поправить права и выполнить `ALTER DATABASE [db] SET ONLINE` вручную.

---

## Что скрипт **не** делает

- Не переносит системные базы.
- Не делает резервные копии (сделайте сами, серьёзно).
- Не проверяет, что места на новом диске хватает.
- Не трогает `tempdb` (там вообще своя логика при каждом старте).
- Не гарантирует, что после переноса всё будет хорошо — это инструмент, а не волшебная кнопка. Глаза и бэкап всё ещё нужны.
